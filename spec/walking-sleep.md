## 1. 심사위원이 직접 확인할 흐름

## 2. 브라우저에서 읽을 기록

### Apple 건강

- 건강 앱의 ‘모든 건강 데이터 내보내기’에서 얻는 XML 또는 해당 XML을 담은 ZIP을 읽는다. 걸음은 `HKQuantityTypeIdentifierStepCount`의 `unit="count"`, `value`, `startDate`, `endDate`를 읽는다. 각 값은 해당 구간에서 센 걸음 수다. `sourceName`, 기기 정보는 출처가 바뀌거나 겹치는지 기기 안에서 판별하는 데 쓴다. [Apple 내보내기 안내](https://support.apple.com/ko-kr/guide/iphone/iph5ede58c3d/ios) · [HealthKit 걸음 정의](https://developer.apple.com/documentation/healthkit/hkquantitytypeidentifier/stepcount)
- Apple 건강은 출처 우선순위를 제공하고 사용자가 조정할 수 있다. 웹 파서에서 공식 앱과 같은 합산을 재현했다고 가정하지 않는다. MVP에서는 같은 기기·출처를 두 기간에 고정하고 ‘선택한 워치 기록 기준’과 같이 표시한다. 출처를 식별할 수 없거나 바뀐 경우 두 기간을 이어 붙이지 않는다. 자정을 가로지르는 걸음 구간은 일자별 배분을 알 수 없으므로 MVP에서는 영향을 받은 날짜를 불완전으로 표시한다. [Apple의 데이터 출처와 우선순위](https://support.apple.com/ko-kr/108779)
- 수면은 `HKCategoryTypeIdentifierSleepAnalysis`에서 한 출처의 `AsleepCore`, `AsleepDeep`, `AsleepREM`, `AsleepUnspecified`와 구형 `Asleep`를 잠든 구간으로 읽는다(XML에서는 앞에 `HKCategoryValueSleepAnalysis`가 붙는다). 같은 수면을 나타내는 포괄 구간과 단계가 겹치면 세밀한 단계 기록을 우선한다. 겹친 분을 두 번 세지 않고, 명시적 `Awake`를 제외한다. `InBed` 단독이면 누워 있었던 구간만 알 수 있다. [HealthKit 수면 범주와 겹침](https://developer.apple.com/documentation/healthkit/hkcategoryvaluesleepanalysis)

### 삼성 헬스

- **웹 MVP의 입력은 삼성 헬스 설정의 개인 데이터 다운로드에서 얻은 파일**이다. 폴더의 CSV를 선택하는 경로를 기본으로 삼고 ZIP이면 내부 파일을 찾는다. Android의 Health Connect 권한 연동과 Samsung Health Data SDK는 별도로 구현하는 경로다. SDK 모델명만으로 내보낸 파일의 판본이나 값까지 확정할 수 없다. [삼성 다운로드 안내](https://www.samsung.com/us/support/answer/ANS10001379/) · [삼성의 Health Connect 연동 설명](https://developer.samsung.com/health/blog/en/accessing-samsung-health-data-through-health-connect)
- 수면의 생성 경로를 확인한다. 삼성 헬스는 웨어러블 없이도 휴대전화의 비활동과 이후 켜짐·움직임 등을 바탕으로 예상 수면 구간을 제시하며, 사용자가 기상 후 이를 확인하고 기록할 수 있다. 출처가 확인되면 ‘휴대전화 사용으로 추정한 구간’, ‘직접 입력한 시간’, ‘웨어러블 측정’, ‘연동 앱 기록’으로 표시한다. 출처를 판별할 수 없으면 ‘출처 미확인’으로 둔다. 휴대전화 추정 구간에서 실제 수면 분·각성 횟수를 계산하지 않는다. 외부 앱도 단계 기록을 쓸 수 있으므로 단계 열만으로 워치 착용을 단정하지 않는다. [삼성전자 수면 FAQ](https://www.samsung.com/sec/samsung-health/) · [삼성 헬스 담당자의 휴대전화 추정 방식 설명](https://r1.community.samsung.com/t5/samsung-health/삼성-헬스-잠드는-시간/m-p/38843779/highlight/true) · [외부 앱 수면 단계 동기화 예시](https://developer.samsung.com/health/blog/en/managing-sleep-data-with-samsung-health-and-health-connect)
- 걸음은 `step_daily_trend`의 `day_time`, `count`, `source_type`을 확인한다. 알려진 형식에서 `source_type=-2`는 여러 기기를 통합한 하루 총계다. 그 행이 있으면 휴대폰·워치별 행이나 다른 요약 테이블을 더하지 않는다. 같은 날짜에 값이 다른 전체 행이 여러 개이고 버전을 가릴 수 없으면 그 날짜는 제외한다. `day_time`을 해당 달력 날짜의 UTC 자정으로 기록한 판본은 그 날짜 라벨을 그대로 쓴다. 통합값을 사용할 수 없으면 ‘통합값 없음’으로 남긴다. 구 SDK 문서는 로그인으로 연결될 수 있다. 앱 버전별 적용 여부는 다운로드 파일과 앱의 일별 총계를 대조해서 확정한다. [삼성 일별 걸음 명세](https://developer.samsung.com/health/android/data/api-reference/com/samsung/android/sdk/healthdata/HealthConstants.StepDailyTrend.html) · [내보내기 구현자의 행 처리 기록](https://github.com/davidmosiah/samsung-health-mcp/blob/main/docs/samsung-source-contracts.md)
- 수면은 세션의 `datauuid`와 단계의 `sleep_id`로 연결한다. 공개된 Galaxy Watch 4 내보내기 사례의 `stage`는 40001 각성, 40002 얕은 잠, 40003 깊은 잠, 40004 REM이다. 실제 헤더에는 긴 네임스페이스가 붙을 수 있고 세션 파일과 단계 파일의 접두사가 다를 수 있다. 파일명의 일부만으로 읽지 말고 헤더, 키, 시각 표현과 코드 표가 함께 맞는지 확인한다. 단계가 없는 세션은 ‘수면 기록 구간’으로만 표시한다. [실제 다운로드 자료를 사용한 연구 §III·표 I~II](https://sbia.org.br/wp-content/uploads/2023/10/pdf/CBIC_2023_paper139.pdf) · [파일별 공개 구현 관찰](https://github.com/Santie-a/health-tracker/blob/master/server/SAMSUNG_FILES.md)
- 확인된 파일명 예에는 `com.samsung.shealth.step_daily_trend.<시각>.csv`, `com.samsung.shealth.sleep.<시각>.csv`가 있다. 단계 파일은 별도 공개 구현에서 `com.samsung.health.sleep_stage`로 표기했다. 세션의 `shealth`와 단계의 `health`를 동일한 고정 접두사로 가정하면 파일 하나를 놓칠 수 있다. [국내 실기 연구의 내보내기 파일 목록](https://dcollection.korea.ac.kr/public_resource/pdf/000000257935_20260326154446.pdf) · [단계 파일 관찰](https://github.com/Santie-a/health-tracker/blob/master/server/SAMSUNG_FILES.md)
- `start_time`, `end_time`, `time_offset`의 표현을 판본별로 확인한다. UTC 밀리초, 현지 문자열에 별도 오프셋을 붙인 값, 날짜를 나타내는 숫자를 같은 변환기에 넣지 않는다. 지원 판본은 헤더와 단위, 자정 전후 한 세션, 화면에서 읽은 하루 총계를 검증 기록에 남긴다. 판본이나 시간 기준을 모르면 영향을 받는 지표를 보류한다.

## 3. 공통 지표와 단위

먼저 걸음의 일별 기록에서 평소와 차이가 보인 기간과 변화량을 살펴보고, 같은 날짜에 신뢰할 만한 수면 기록이 있으면 밤별 길이와 변동을 함께 본다. 두 기간의 평균만 계산한 화면에서는 그 기간과 평균 차이만 말한다. ‘언제부터’라는 설명은 날짜별 기록이 뒷받침하는 관측 구간으로 한정하고 중간 누락일을 표시한다. 두 지표에 변화가 겹쳐도 개인의 우울 여부나 시작일은 결정할 수 없다. [걸음·수면 연구의 결과와 적용 범위](../research/07-walking-sleep/REPORT.md)

기준일 D는 비교에 사용할 수 있는 가장 최근의 **완료된 현지 날짜**로 정하고 화면에 날짜를 쓴다. 아침에 파일을 내보냈다면 진행 중인 그날의 걸음 수는 전날과 비교하지 않는다. 최근은 D−13일부터 D까지 14일, 평소는 D−89일부터 D−14일까지 76일이다. 개인이 선택한 한 플랫폼 내에서 비교하며, Apple과 삼성의 기록을 합쳐 한 사람의 과거를 만들지 않는다.

| 화면 지표 | 일별·밤별 산식 | 두 기간의 비교 |
|---|---|---|
| 기록된 걸음 수 (보/관측일) | 현지 달력일별, Apple은 선택 출처의 유효한 구간 걸음 합계, 삼성은 확인된 기기 통합 일별 값. 완전 중복은 한 번만 세고 같은 출처의 부분 겹침이 해소되지 않으면 해당 날은 제외 | 각 기간의 걸음 합 ÷ 유효 관측일. 최근 평균−평소 평균을 보 단위로 표시. 평소 평균이 양수일 때만 상대 변화율도 표시 |
| 주수면 추정 시간 (분/관측 밤) | 주수면 한 회차 안에서 잠든 구간의 합집합 길이. 명시적 각성은 제외한다. 지속시간은 오프셋을 반영한 실제 경과 분으로 구한다. 누락 구간을 잠으로 채우지 않는다 | 각 기간의 유효한 밤별 수면 분의 평균과 그 차이. 단계 일부가 빠진 밤은 ‘관측된 수면 ○분’으로만 표시하고 완전한 밤과 평균내지 않는다 |
| 기록상 잠든 시각 (현지 시각) | 같은 주수면의 첫 확인된 수면 구간 시작. 예를 들어 23:50과 다음 날 00:10을 같은 밤 기준 자정 −10분, +10분으로 펼친다. 실제 잠든 순간과 기기의 판정에는 차이가 있을 수 있다 | 기간별 평균을 다시 시각으로 표시하고, 변화는 부호 있는 분으로 표시. 시간대가 불명확하거나 야간·주간 수면을 일관되게 대응시킬 수 없으면 보류 |
| 잠드는 시각의 변동 (분, 보조 지표) | 위와 같이 펼친 밤별 입면 시각의 표본 표준편차. 값이 클수록 그 기간의 입면 시각이 더 흩어져 있었다는 뜻 | 평소와 최근의 표준편차 및 차이를 분으로 표시. 평소 변동이 0분일 때도 계산할 수 있다. 연구에서 사용하는 수면규칙성지수(SRI)와 구별 |

**관측 품질도 결과에 포함한다.** 최소한 ‘걸음 10/14일 · 수면 8/14밤’처럼 지표별 분모를 표시한다. 기록 없음은 결측으로 둔다. 실제로 하루 전체를 측정했고 값이 0이라는 근거가 있을 때만 0보를 쓴다. 행 하나가 있다는 사실만으로 하루 종일 휴대·착용했다고 단정할 수 없다. 최근 5일·평소 7일이라는 기존 코드의 최소 관측 수는 팀의 잠정 표시 기준이다. 두 기간의 요일 편중이나 기기 변경이 크면 기록일 평균만 설명하고 생활 전반에 관한 결론은 보류한다.

수면 날짜는 주수면이 시작된 밤 기준으로 표시하고, 자정 직후의 입면은 전날 밤에 붙인다. 삼성에서는 세션 키를 우선 사용한다. Apple에서 세션이 명시되지 않은 경우 한 출처의 취침 구간이나 일관된 단계 열로 주수면을 확인한다. 둘 이상의 후보가 있고 주수면을 식별하기 어려운 밤, 낮잠과 야간 수면이 섞인 밤, 교대·여행으로 시각 기준이 불명확한 밤은 따로 표시한다. 주수면의 시작·끝이 알려져도 안쪽 단계가 비었으면 ‘수면시간’과 ‘세션 길이’를 구분한다.

## 4. AI에 맡길 일과 데이터 경계

팀 코드가 유효성 검사, 기간 선택, 수치 계산과 표시를 맡는다. AI는 충분한 기록이 있는 지표와 사용자 답변에 맞춰 **다음 질문 하나**를 고른다. 보고서의 숫자는 계산 결과에서 렌더링하고, 사용자가 확인한 생활 맥락을 별도로 표시한다. 잠드는 시각만으로 번아웃·우울을 추정하거나 대화에서 PHQ 점수를 만들지 않는다. 시험·근무·여행·착용 방식처럼 여러 설명이 가능하다. [학술 근거와 적용 범위](../research/07-walking-sleep/REPORT.md)

대회 기준은 동의 여부와 관계없이 외부 AI에 실제 개인정보·민감정보를 입력·전송하는 것을 금지한다. 외부 서비스에는 가상 데이터나 개인을 알아볼 수 없도록 처리된 데이터를 사용하는 규정이다. **팀의 대회용 구현 제안은 외부 AI에 합성 사례와 미리 작성한 상황 선택지만 보내는 것**이다. 파일 출처와 무관하게 개인의 자유 입력도 건강·상담 정보를 포함할 수 있다. 개인 파일 경로는 로컬 계산과 결과 열람으로 끝내고, 데모 서버는 허용된 사례·선택지 ID에서 합성 대화를 구성한다. 이름 삭제, 요약 수치 전송, 클라이언트의 ‘샘플’ 표지만으로 전송 여부를 결정하지 않는다. ## 5. 구현 순서와 시연 통과 조건

1. **개인 파일과 합성 시연을 분리한다.** 네트워크 기록에서 개인 파일 선택, 첫 질문, 리포트 생성 어느 시점에도 개인 요약·자유문이 서버나 외부 AI로 가지 않는지 확인한다. 합성 경로에서는 서버가 알고 있는 사례와 선택지로 대화가 끝까지 이어져야 한다.
2. **동일한 가상 생활을 두 파일 형식으로 작성한다.** 삼성의 전체 6,000보와 기기별 4,000·3,000보가 함께 있으면 전체 행의 6,000보를 표시한다. 이에 대응하는 Apple 단일 출처의 2,500보와 3,500보를 읽어도 결과는 6,000보여야 한다. 두 플랫폼에서 23:50~02:00 수면, 02:00~02:20 각성, 02:20~06:50 수면이면 주수면은 **400분(6시간 40분)**, 입면은 **23:50**이다. 세션 전체는 420분이다. 이 값은 손계산한 검수 예시다.
3. **숫자를 내지 않아야 할 입력도 검사한다.** 수면 단계 없는 세션, 누락일, 중복 수면 단계, 날짜를 넘긴 걸음 구간, 기기 교체, 기준선이 0인 변화율, 오프셋 전환을 포함한다. 예를 들어 01:30(UTC−5)에서 03:30(UTC−4)은 실제 경과 60분이다. 품질 문제가 있는 지표는 대화의 질문 후보에서도 제외한다.
4. **지표 하나만 있어도 흐름을 살린다.** 수면 기록이 없는 스마트폰 사용자는 걸음 기록만 검토한다. 같은 가상 사례에서 ‘야간 근무’와 ‘기기 미착용’을 각각 선택해 후속 질문과 리포트가 달라지는지 본다. 모든 숫자가 원자료에서 다시 계산되고 사용자 발언의 출처를 확인할 수 있을 때 시연한다.
5. **지원 상태를 정확히 쓴다.** Apple과 삼성 각각에 대해 ‘가상 파일로 계산 검증’과 ‘특정 앱 버전의 다운로드 파일 및 앱 화면과 대조’를 구분한다. 실제 자료 대조는 기기 안에서 할 수 있으며, 저장소·외부 AI·소개서에는 합성 자료를 쓴다. 마감 시점에 검증하지 못한 플랫폼은 구현 현황과 향후 지원 항목을 구분해 소개한다.

**현재 확인한 동작(2026-11-22).** 저장소의 Apple 합성 XML로 평소 8,298보 → 최근 4,234보, 수면 7시간 11분 → 5시간 13분, 입면 00:16 → 01:30을 재현했다. 삼성 입력 파서와 양사 실기기 앱 화면 대조는 아직 없다. 현재 Apple 코드는 하루 출처별 합계 중 최댓값을 고른다. 합성 예시에서 겹치지 않는 워치 1,000보와 폰 500보를 주면 1,000보가 나온다. 오프셋 전환 예시도 현재는 120분이 나온다. 개인 파일에서 세션을 열면 곧바로 대화 API를 부르고, 서버에 Gemini 키가 있으면 요약과 대화가 전달되는 경로가 있다. 위 통과 조건은 이 차이들을 기준으로 삼는다.
